# 测试和迭代

这里只放有记录的结果。测试案例本身来自客户提供的匿名历史线索，属于保密资料，所以我只给汇总的数字。测试和迭代是团队一起做的，我主要负责检查测试案例的内容和参考答案。

## 怎么打分

每个案例都和事先写好的参考答案对比，分五项打分：理解、下一步、时机、材料、邮件，每项 0 到 2 分，满分 10 分。某一项不适用时记 n/a，满分就变成 8 分。

| 分数 | 意思 |
|---|---|
| 2 | 对，可以直接用 |
| 1 | 部分对，需要顾问改 |
| 0 | 错了，或者有害，比如最后一封邮件发完还继续追，或者编了事实 |

决策点的参考答案主要来自客户当时真实的做法，其中 2 个客户明确确认过。边界情况的参考答案是我们按规则写的，客户没有确认。

## 测试后改了什么

| 发现的问题 | 怎么改的 |
|---|---|
| 一封邮件里问了两个问题，或放了两个行动按钮 | 规定一封邮件只留一个问题或一个行动按钮 |
| 把没核实过的视频内容写成了事实 | 只写主题，提醒顾问发之前自己看一遍 |
| 邮件里直接出现了联系人的编号 | 联系人一律用 `[Name …]` 占位 |
| 从下载的问卷主题直接推断客户的痛点 | 改成写“还看不出来”，主题只作为线索 |
| 顾问的口吻一会儿“我们”一会儿“我” | 顾问写信用“我”，只有提到公司时才用“我们” |
| 知识库里还留着真实人名 | 删掉，重新生成 K1 |
| 规则里的待确认问题把测试答案透露了出去 | 改成中性的说法 |
| 日报和周报对同一个线索推荐了不同的材料 | 统一成同一套材料字段，两边共用 |
| 数据截止早于运行日期时，把没记录当成没做 | 过期分成“已确认”和“未确认” |

## 还没测到或还没解决的

- 没有接入真实的 CRM 和 OneDrive，所以实时读取和材料同步都没测过。
- 不发邮件、不写 CRM 是设计上的限制。没有连到真实系统，没法在真实系统里验证。
- 邮件写得是否符合客户的风格，要顾问来判断，我们没有自动评分。
- 样本小：系统测试只有 8 个线索，其中 2 个进了需求日志。雷达自己的规则也写了，少于 10 个线索不足以下结论。
- 10 月 19 日写测试报告时，日报和周报的一致性还没正式测。整理作品集时，我对照了同一天的日报和周报：8 个线索的分类一致，4 个过期未确认、1 个要内部核实、3 个等待或已变冷。这只是对照两份输出，不算正式测试。
- 10 月 22 日交付最终版本之后，没有再完整测一遍；第 3 轮提出的修改有没有全部落实，也没有确认。
