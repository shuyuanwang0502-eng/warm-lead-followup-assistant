# 工作流设计

这里只讲设计思路，没有放 Skills 原文和客户知识库的内容。公开版里我把 Skill 名字前面的客户前缀去掉了。

## 哪些是 Claude 平台的，哪些是我们做的

| Claude 平台自带 | 我们设计和编写的 |
|---|---|
| Skills 机制：根据描述自动加载说明文件 | 10 个 Skills 的业务逻辑、判断顺序、输出格式和底线规则 |
| Projects：共享上下文文件 | 知识库：K2 规则、K3 分类体系和 K1 的结构由我设计，K1 的逐条内容由队友整理 |
| 定时任务 | 每日、每周、每月任务的提示词，读哪些数据，什么时候通知 |
| Artifacts：渲染交互页面 | 看板放哪些内容：计数、分类、线索卡片、标签页、德英切换 |
| 桌面 App 读本地文件、连接器 | 测试数据的约定（一个线索一个文件，加一个总目录），哪些文件只读、哪些可以写 |

## 10 个 Skills

其中 lead-analysis、next-action、daily-reminder 和 weekly-briefing 是我写的，其余由队友负责。

| Skill | 做什么 | 输出 |
|---|---|---|
| `lead-analysis` | 理清时间线；分出强信号、弱信号和没信号（扫描器几分钟内把链接全点一遍的不算）；看线索走到跟进节奏的哪一步；找出特殊情况和缺的数据 | 线索概况和现状：阶段、主题、痛点（看不出来就写“还看不出来”）、参与程度、数据缺口 |
| `next-action` | 按固定顺序检查规则：已成交、线索回复了没人回、刚开完会、线索推迟、有约定日期、发过报价、标准节奏、聊过之后没动静、冷线索。碰到第一条符合的就停 | 做什么、什么时候、用什么渠道、谁来做、依据哪条规则、把握有多大 |
| `content-matching` | 先判断这时候该不该发材料，再按主题、痛点和阶段去找；对方已经有的、没批准的、只能内部用的都去掉 | 四栏：现在可以发的、满足条件后可以发的、只作内部参考的、理由和限制；另加一条内容需求记录 |
| `followup-email` | 写 80 到 180 词的德语草稿：接着上一次真实的接触，只讲一个新观点，最多问一个问题或放一个行动按钮 | 邮件主题和正文，人名和链接用占位符 |
| `pipeline-triage` | 一次看多个线索，快速分级 | A 今天处理、B 本周处理、C 先内部核实、D 等待 |
| `daily-reminder` | 每日提醒：过期（已确认、未确认）、今天到期、窗口期内、要内部核实、暂时没事，每个线索只算一次 | 每日看板，做不了看板时给文字提醒 |
| `weekly-briefing` | 每周看全部线索，调用上面五个 Skills，顺便写内容需求日志 | 每周看板和 `content_demand_log.csv` |
| `content-gap-radar` | 对比线索需要什么材料、材料库里有什么 | 月度汇总文件和看板数据 |
| `library-sync` | 从客户的 OneDrive 找出新增、修改和删除的材料，起草新条目，新条目一律标“待确认” | 更新后的材料库和同步报告 |
| `content-library-instructions` | 材料打标的规范：有哪些列、能填哪些值、怎么校验。给 `library-sync` 用 | 无 |

## 知识库（客户内部资料，不公开）

| 文件 | 用来做什么 | 结构 |
|---|---|---|
| K1 材料库 | 推荐材料只能从这里选 | 每条：编号、能否对外发、类型、主题和子主题、面向谁、痛点、适合什么情况、销售阶段、用途、摘要、关键词 |
| K2 跟进规则 | 判断时机和动作的依据 | 销售流程、四封邮件的标准节奏（按天数）、什么时候算变冷、特殊情况、写邮件的原则；每条标了来源 |
| K3 分类体系 | 大家共用的词表 | 10 个主题、20 个痛点、销售阶段、建议用途 |

设计 K2 时，我把每条规则的来源分成三类：客户确认过的、从数据里观察到的、我们团队的假设。这样客户可以一条条确认，哪些还只是我们的猜测也一目了然。Skills 都是从知识库读规则，规则变了只要改知识库，不用动 Skills。

## 底线规则

- 只给建议，不执行：不发邮件，不写 CRM，看板上写明“这是静态快照”。
- 不报价，不承诺，不编造会议内容、数字和链接。材料的细节只写材料库里写明的。
- 参考日期之后的信息一律当作不存在。记录里没有，不等于没做，标成“未确认，先核实”。
- 每个线索只归到一个状态，总数能对上，比如 8 = 0+4+0+0+1+3。
- 之后才可能发生的步骤只作为备注，不提前变成待办。
- 内容需求日志里不写人名、公司名，也不引用原话。

## 迭代中改出来的几处设计

- 过期分成“已确认”和“未确认”。测试数据比运行日期早五天，早期版本会把没记录的动作当成没做，建议顾问重发。
- 材料推荐统一成同一套字段。日报和周报一度对同一个线索推荐了不同的材料，统一之后两边共用同一套规则。
- 内容需求日志接上月度雷达。“没有合适材料”原来只是一句备注，现在变成可以累计、可以汇总的数据。
